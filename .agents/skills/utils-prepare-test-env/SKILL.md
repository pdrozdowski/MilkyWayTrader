# Prepare the Playwright test environment

Use this skill to establish that the repository's real Playwright test setup can run. Work from the repository root and preserve the test runner's configured lifecycle. Read the local-Supabase and Playwright rules in `context/foundation/testing.md` and `context/testing/playwright-principles.md` when available.

Before checks, create a fresh `run_id` and a run folder `.cache/playwright/env-preflight/<run_id>/` containing `execution-status.json` and append-only `execution-log.jsonl`. Give checks stable IDs (`ENV-01` onward), list `depends_on`, write `RUNNING` before a check and its final status immediately after it, and never treat a previous run's `PASS` as current evidence. Preserve screenshots and other successful artifacts in the run folder. Use `PASS`, `FAIL`, `RETRYING`, `BLOCKED`, or `SKIPPED`; include a reason for blocked/skipped steps. Set overall status to `PASS` only when all required checks pass; otherwise record `PARTIAL` or `BLOCKED` with the specific blocker. If writing the ledger fails, keep it in memory and disclose that. Send brief progress updates when phases complete or an environment failure blocks progress.

## Prepare and verify

1. **Check the runtime.** Record Node, npm, Playwright CLI, and installed Chromium versions/paths. Verify Node can spawn its own `-v` child process using `spawnSync(process.execPath, ['-v'])`. Keep this separate from Vite/esbuild and browser checks. If the spawn fails with `EPERM`, record it and retry that exact smoke check through the host's escalation path; a passing generic spawn still does not prove Vite/esbuild can spawn.
2. **Check the test port.** Inspect port 8081 before starting tests. The project's `playwrightConfig.ts` uses `reuseExistingServer: false` and strict port binding, so the runner needs the port free. Identify any listener and its owner; do not kill unrelated processes or start a competing Vite server.
3. **Start local Supabase.** Confirm Docker Engine is available, then run `npx.cmd supabase start --exclude vector` from the project root and confirm `npx.cmd supabase status`. If the CLI is blocked specifically from writing its own local telemetry/config file with `EPERM`, retry only that exact command through the host's escalation path. If the Docker Desktop service/engine is stopped and cannot start in the current session, stop here and ask the user to start Docker Desktop with its Linux engine; do not run UAC/run-as commands or change service permissions. Use only the local Docker stack. `npm.cmd run test:ui` resets/migrates this local database; it must never target a remote Supabase project. Do not print `.env.test` values, credentials, session artifacts, or tokens.
4. **Verify Chromium itself.** Use the installed Playwright package to launch Chromium, navigate to a local `data:` page, and create a small screenshot in the run folder. This proves browser launch, navigation, and screenshot writing; listing tests alone does not. If launch fails with `spawn EPERM`, retry only this browser smoke check through the host's escalation path.
5. **Run the configured test server through Playwright.** The suite owns Vite's lifecycle using `npm run dev:test-nolog -- --host 127.0.0.1 --port 8081 --strictPort`, configured in `playwrightConfig.ts`. Its `webServer.url` check is the HTTP readiness probe; keep that runner-owned server alive through the full suite and teardown. Run `npm.cmd run test:ui`; do not launch a competing server. Confirm the global setup prints exactly one `PLAYWRIGHT_SUITE_DB_RESET_COUNT 1`, the test fixture setup is reached, and the runner reports results. Inspect its current report before proceeding.
6. **Handle Windows `spawn EPERM` narrowly.** If the default `npm.cmd run test:ui` fails specifically while Vite/esbuild starts, rerun that exact test command once through the host's `require_escalated` path. This suite-owned retry keeps its Vite process alive for the complete test run. If the Vite command must be diagnosed separately, use the exact command above, probe `http://127.0.0.1:8081`, record readiness and ownership, then stop only the process started for that diagnostic before rerunning Playwright. Escalate a separate operation only after that operation independently reports an access restriction. Keep certificate verification and other security settings unchanged; never escalate unrelated commands.
7. **Capture failures and stop safely.** For each failure record the step, command, permission mode and escalation approval state (approved/denied/unavailable), working directory, relevant versions, exit code or signal, exception name/message/stack and code/errno/syscall, bounded sanitized stdout/stderr, timeout, artifact/report paths, and reproducibility. Include browser state/viewport when relevant. Classify it as environment/setup, test failure, or `UNKNOWN` when evidence is insufficient; record root-cause confidence. Retry a transient environment error once in a fresh process after cleaning only resources owned by this run. If Docker/Chromium/dependencies remain unavailable, mark dependent steps blocked and report the exact recovery action; do not edit application code or weaken tests to mask setup failures.

## Handoff

- If environment checks pass, hand off to `cicd-run-tests` for the full product suite or run the requested Playwright command. For a current `TEST_FAILURE` report, use `cicd-fix-tests` to repair the smallest product defect, then return to `cicd-run-tests`.
- If checks are blocked, report completed checks, the precise blocked step and error, and the command or user action needed to continue. Do not claim Playwright passed unless the browser tests actually completed.

## Source procedure coverage

This skill extracts the environment preparation and recovery procedure from `responsive-ui-audit` only. The source's viewport capture, DOM inspection, visual integrity, interaction audit, defect classification, and UI repair phases remain in that skill.
